1. Executive Summary & Verdict

This audit evaluates the current Appendix B.1 Use Case Diagram and B.2 Use Case Descriptions (Version 0.3) against the concrete codebase implementation across apps/backend, apps/frontend, and packages/shared-types.

Area Audited Status Key Findings & Recommended Actions
Core Functional Scope Fully Aligned All 16 use cases (UC-01 to UC-16) have concrete backend routes and frontend UI implementations. The functional scope accurately reflects the built product.
Actor Generalization Fully Aligned The actor inheritance Registered Driver —▷ Driver perfectly matches the codebase's anonymous/guest mode (session.isGuest = true) vs. authenticated sessions.
Secondary System Actors Needs Update Supabase Auth is missing from the diagram despite powering UC-12 (Register/Login) and UC-13 (Manage Profile). Browser Geolocation should be explicitly bound to UC-01 & UC-03.
Filtering Relationship (UC-07) Needs Update UC-07 (Filter Carparks) is currently drawn as a detached use case. In UML and code, filtering is an <<extend>> to UC-01 (Search Destination).
Weather Dependencies (UC-05) Needs Update UC-05 (Get Weather Forecast) is currently only included by UC-15. However, the codebase and UI display live weather warnings in both UC-09 (Navigation) and UC-06 (Carpark Details).
Alert Lifecycle (UC-14) Needs Update Labelled passively as "Receive Availability Alert". In reality, the user configures/subscribes to monitored carparks in CarparkDetailPage, and receives toast alerts in the app shell.
Final Verdict: Highly Viable, Requires UML Precision Tuning
The existing SRS use case foundation does not require a conceptual rewrite. However, updating the diagram and descriptions to correct UML association semantics (specifically <<extend>>, missing secondary actors, and multi-consumer weather/routing inclusions) will eliminate grading penalties under NTU SC2006 OOAD criteria.

2. Detailed Subsystem Analysis: SRS vs. Codebase

2.1 User & Authentication Subsystem (UC-12, UC-13, UC-10, UC-11)

  • Guest vs. Registered Actor: In AuthContext.tsx, unauthenticated drivers can perform destination searches, view carparks, apply filters, and navigate. Registered Driver inherits these and gains access to /api/favourites (UC-10, UC-11), /api/users/me (UC-13), and /api/alerts (UC-14). This cleanly verifies the actor inheritance in UML.
  • Missing External Identity Provider: UC-12 and UC-13 connect only to the human actor. In production, requests hit Supabase GoTrue Auth (apps/backend/src/modules/auth/auth.service.ts). An external actor <<system>> Authentication Service (Supabase Auth) must be added.
  • Favourites to Search Flow: In FavouritesPage.tsx, tapping a saved location directly triggers a search for that destination. In UML, this can be represented as UC-11 •••> UC-01 <<invokes>>.

2.2 Destination Search & Recommendation Subsystem (UC-01, UC-07, UC-15, UC-16)

  • Search Orchestration (UC-01 & UC-15): search.service.ts acts as the orchestrator endpoint (GET /api/carparks/nearby). When sort = 'recommended', it delegates to rankCarparks() (UC-15). UC-01 rightly includes UC-15.
  • Filtering Semantics (UC-07): The SRS lists UC-07 as a standalone use case. However, carparks cannot be filtered without candidate carparks being retrieved first. UC-01 alternative flow UC-01.AC.2 explicitly notes "Driver applies filters". Therefore, UC-07 must extend UC-01 via <<extend>>.
  • Historical Availability (UC-16): Matches the code in historical-availability.ts, validating that at least 4 distinct historical records exist for the same day-of-week and hour bucket before returning an availability ratio.

2.3 Route & Navigation Subsystem (UC-03, UC-04, UC-08, UC-09)

  • Multi-Modal Route Composition: In NavigationPage.tsx and useNavigationRoutes.ts, navigation comprises both a driving leg ($Origin \rightarrow Carpark$, UC-03) and a walking leg ($Carpark \rightarrow Destination$, UC-04). UC-09 correctly includes UC-03 and UC-04.
  • Live Weather in Navigation: NavigationPage.tsx imports useWeather to warn drivers: "Showers expected... Bring an umbrella" (SRS page 15). The current diagram lacks this connection. UC-09 must include UC-05 (Get Weather Forecast).
  • Carpark Selection (UC-08): In CarparkCard.tsx, tapping "Navigate" transitions directly to navigation (UC-09), while tapping the card opens details (UC-06). UC-08 is simply an interaction step that should bridge into UC-06 and UC-09.

2.4 Carpark Availability & Alerts Subsystem (UC-02, UC-06, UC-14)

  • Real-Time Data Poller: UC-02 (Get Real-Time Carpark Information) is fed by background polling every 60 seconds (availability/poller.ts). It is correctly included by UC-15 (Recommendations) and UC-06 (Details).
  • Alert Management (UC-14): In `CarparkDetailPage.tsx`, registered users toggle availability notifications via `AvailabilityAlertControl`. The backend checks threshold tier transitions (`hasSignificantAvailabilityChange`). Naming should be updated to "Manage & Receive Availability Alerts".
